# Операции и доступ сотрудников

## Принцип

В AURA RUSH нет клиентских «админок», которые дают полномочия сами по себе.
Роль вычисляет сервер в `StaffPolicy`, а каждый запрос проходит через
rate-limited remote contract. Обычный игрок не получает ни интерфейс OPS, ни
операционный снимок, ни возможность выполнить действие.

Текущий минимальный контур намеренно мал:

| Роль | Возможности |
|---|---|
| Игрок | Нет доступа к операциям |
| Поддержка | Состояние сервера и health-сводка |
| Модератор | Health-сводка и последние audit-записи текущей сессии |
| Администратор | Всё выше плюс два заранее утверждённых объявления |
| Владелец | Те же видимые действия; право менять policy остаётся серверной конфигурацией, а не игровым UI |

В панели нельзя вводить произвольный текст, выполнять код, выдавать валюту,
изменять прогресс, кикать игроков или редактировать флаги. Это осознанное
ограничение: операционный инструмент не должен становиться новой поверхностью
для эксплойтов или случайного вреда.

## Настройка перед закрытым тестом или публикацией

1. В защищённой production-конфигурации заполните `Config.Admin.OwnerUserIds`
   реальными Roblox UserId владельцев **либо** укажите `GroupId` и пороги рангов.
   Пустой список в репозитории — безопасный default и не является ошибкой.
2. Никогда не коммитьте персональные UserId, private group data или секреты в
   публичный репозиторий. Для production используйте отдельно защищённый config
   слой и code review.
3. Откройте private server под владельцем. После первого snapshot должна появиться
   небольшая кнопка `OPS`; у обычного аккаунта она не создаётся.
4. Проверьте роль, количество игроков, состояние раунда, rejected remote count и
   persistence failures. Только затем проверьте одно шаблонное объявление.
5. Убедитесь, что audit-запись содержит ожидаемый action/result и не показывает
   inventory, UserId, receipt ID, round ID или другой лишний персональный контекст.

## Что видно в OPS

- состояние и шаг server bootstrap;
- игроки, фаза раунда и uptime;
- сводка accepted/rejected/outbound remote-вызовов;
- агрегированные счётчики profile, receipt, Atelier и Community DataStore операций;
- heartbeat p95;
- до 12 последних audit-записей только для ролей с правом `view_audit`.

Audit-история живёт только в памяти данного сервера и ограничена 80 записями по
умолчанию. Это operational trace, а не заменитель внешнего защищённого аудита.

## Реакция на инцидент

| Симптом | Сначала проверить | Безопасное действие |
|---|---|---|
| Много rejected remotes | Счётчик сети и клиентские ошибки | Не отключать validation; зафиксировать тип/время/версию и воспроизвести в private server |
| Persistence failures > 0 | OPS и server Output | Не выдавать компенсации вручную; проверить retry/budget и read-only status, затем использовать идемпотентный путь награды |
| Серый экран у игрока | `AuraRushBootState`, `AuraRushRuntimeState`, свежий Player/Studio log | Следовать [RUNBOOK](RUNBOOK.md#серый-экран-или-вход-без-ui) и не публиковать догадки как фикс |
| Нужна массовая коммуникация | Шаблон `maintenance_soon` или `update_ready` | Использовать только утверждённый шаблон и cooldown; не писать free text |

## Обязательные границы

- `OwnerUserIds`, group ranks и permissions проверяются на сервере при входе и
  кэшируются не дольше 60 секунд.
- Любое действие проверяет роль повторно и имеет server audit record.
- Remote payload ограничен глубиной, размером и частотой до handler-а.
- В production staff policy меняют через reviewed deployment, а не в живой сессии.
- Расширять набор админ-действий можно только после отдельного threat model,
  permission matrix, audit trail и негативных тестов.
